# DSH 梦核卧室实验：实时桥奏效，QA 工作流仍需改进

## 结论与范围

**本 PR 的主要验证结果是：关闭第三方插件自带的建模 skill 后，DSH 仍能通过它的实时桥工具与我们的 skill 完成梦核卧室的建模、查看、保存和重新打开。** C 组正式运行实际加载了我们的 `blender-asset-workflow`，126 次调用后正常交付。这证明在本案例中，插件自带建模 skill 可以由我们的 skill 替代，实时执行能力和建模工作流可以分开组合。

桥的作用已经得到实际调用和产物验证：保留场景及执行上下文，在场景内增量修改并取回画面，缩短了“修改—观察—再修改”的执行链路。C 使用了 54 次 `blender_rt_cmd`、10 次 `blender_rt_do`、17 次 `blender_rt_see`；它验证的是插件桥工具组合，不能将结果全部归给单一 worker 接口。B 另有成功启动命名 worker 并在其中执行建模的记录，使用的同样是第三方插件实现。

**这项成功验证与“QA 打转已被修复”“几何没有穿模”“完整插件功能已被替代”是不同结论。** A、C 的审阅过程不同，C 交付后仍检出穿模；当前证据足以确认组合可行，尚不足以证明普遍的效率、质量或完整功能等价。

本 PR 保存实验条件、成图、脱敏轨迹和只读检查证据，不修改正式 `skills/` 或本次快照，也不人工修复场景。B 组发生中断并经追加指令续接；中断只作为实验条件记录，不作为本报告的主要问题或成因结论。

## 本 PR 隔离了什么，解决到了哪一步

| --- | --- | --- |

| 实时执行路径 | 提供第三方桥的依赖配置和复现步骤，验证桥工具＋我们的 skill 能完成本案例 | 本 PR 未加入独立自研 worker 桥代码；使用的仍是第三方实现 |

| QA 反复迭代与停止条件 | 保存 A/C 的过程差异，定位可缩短执行链路的机制与遗漏检查 | 没有修改独立审阅、返修预算或停止逻辑；不能宣称 QA 打转已被代码修复 |

因此，本 PR **完成了插件 skill 的有效隔离，并验证了一条能完成任务的桥＋skill 路线**；它交付的是配置、实验和证据，不能写成已交付 QA 根治补丁。

## 为什么接桥后看起来没有继续 QA 打转

这里要区分执行成本、实际审阅行为和是否修复停止条件。

**执行层面的机制成立。** 插件的实时内核可跨调用保留场景和辅助函数，修改后可以直接回帧；不必每个小调整都经外部脚本启动、读取文件、渲染、收集日志再看图。C 中后续调用复用了 `K` 上保存的建模函数，`do`／`see` 和 `execute_code` 在活场景里推进修改。A 的轨迹则记录了多次脚本改写、重建、预览/成图渲染与日志检查。由此可以合理推断，桥减少了执行与反馈的往返成本；单次总耗时不能隔离测出这项收益。

**两组实际执行的 QA 不相同。** A 在第 179 次调用启动独立 reviewer，之后有 14 次 `list_agents` 轮询，并在第 235、267 次调用要求新候选的定向复核，伴随新的修复、渲染和哈希更新。C 没有记录 `subagent`、`list_agents` 或 `send_message` 调用，最终报告声明 `self-check only; no independent reviewer available`。C 在完整审计报错后改用范围较窄的自查并交付，交付后仍有相交证据。[执行与审阅对照](results/execution-review-evidence.json)列出这些事实。

因此，“C 较快结束”可能同时包含**实时反馈更直接**与**少做了独立 QA**两方面，不能全部记作桥的优化收益。A 本次也正常结束，并非已证实无限循环；C 也不是停止检查前已经解决了所有问题。

**桥没有自动改写 QA 的停止策略。** 它能使每轮检查和修改更便宜、更容易观察；要减少无效打转，还须由 skill 明确检查范围、阻断项、有限返修和交付条件，同时避免通过省略必要 QA 换取更快结束。这是下一 PR 要验证的工作流改进。

统计边界如下：

- B 是中断与改变条件后的续接；A/C 的 QA 和渲染路径也不同。因此可以报告各次实际记录的 token，不能把差额全部解释成桥节省的 token，更不能证明省掉必要 QA 后的结果质量等价。

## 已有证据

三组使用相同卧室需求正文。A 删除强制用桥前缀；B、C 保留原有完整提示词。DSH 为 0.2.1-rc.5，Blender 为 5.2.2 LTS，第三方插件为 3.0.4；实际模型 ID 与模型采样参数未知。完整成图和条件见 [RESULTS.md](RESULTS.md)，版本、提示词及产物校验值见[证据清单](results/evidence-manifest.json)。

| 组别 | 配置与实际 skill 加载 | 过程及结果 | 能支持的判断 |
| --- | --- | --- | --- |
| A | 未安装 DSH Blender 插件；加载我们的 `blender-asset-workflow` | 正常完成，83 分 39 秒、271 次调用，无 `blender_rt_*` 调用；记录到独立审阅调用 | 我们的 skill 可以通过普通 Blender 脚本工作 |
| B | 原版完整插件；预检确认两种 skill 都可用；正式运行仅加载 `blender-modeling` | 原运行 75 次调用后中断；原会话续接再调用 10 次并正常完成，追加了恢复指令且改变渲染设置 | skill 可被发现不等于实际被选中；续接结果不能用来做原条件的效果或耗时排名 |
| C | 插件隔离副本仅关闭自带 skill 注册；加载我们的 `blender-asset-workflow` | 正常完成，约 30 分 27 秒、126 次调用，含 17 次 `blender_rt_see` 和 29 次 `read_image`；自查后仍有穿模 | 桥＋我们的 skill 已完成本案例，可替代插件自带建模 skill；几何验收仍需改进 |

每组只有一次实例，运行时间、建模路径和检查范围不同，不能用调用次数或耗时直接证明桥更快、skill 更优。历史 67 分钟／201 次、早期 95 次运行单列于结果页，不混入三组统计。A/B 没有执行与 C 相同的指定对象几何检查，不能据此给三组排穿模数量名次。

### 1. Skill 的发现与实际选择是两件事

B 的预检实际调用并读到了两种 skill，正式运行却只调用了插件的 `blender-modeling`。C 的正式运行第 1 次调用加载的是我们的 `blender-asset-workflow`。此前仅把同名禁用空壳放入嵌套目录的做法没有成功覆盖插件 skill；126 次运行是在隔离插件副本中关闭 `registerBundledSkill(ctx)` 后得到的。

这些记录能证明实际执行入口不同，不能证明固定的同名覆盖顺序，也不能把 B 的选择解释成我们的 skill 不可用。B 选择插件 skill 本身不构成错误，但会影响实验归因。只检查文件清单、安装状态或模型的口头表述，会把配置意图误当成执行事实。

### 2. C 的问题发生在对象关系，单体公式没有表达这些约束

C 的曲面确实由参数公式生成，但公式分别描述窗帘、窗框、枕头和兔子的形状。它们没有自动表达相互避让、支撑、净空或允许接触的关系。

第 57 次调用为改善可见性，把所有 `Bunny*` 对象沿 X 方向移动了 **1.20 m**。该调用没有执行兔子与目标位置枕头的碰撞检查；后续最终自查也没有覆盖这组关系。第 111 次调用重新生成四个枕头并验证非流形边数为零，同样没有验证它们与邻居的空间关系。

对 C 最终保存文件的[只读表面检查](results/arm-c-selected-surfaces.json)确认：两侧窗帘分别与窗框、外饰线和横档发生表面穿越；兔子身体与两个右侧枕头、头部与右后枕头发生表面穿越；四个枕头的六组配对也存在表面穿越。16 个指定配对中 15 个检出严格的三角形边／面穿越，**这是配对证据，不是 15 个独立视觉缺陷，也不是穿透深度或严重度排名**。枕头间的接触意图仍需结合画面判断。

检查在世界坐标中使用求值后的几何，临时将窗框等曲线转换为网格，再验证 BVH 候选三角形；没有修改或保存场景。未检出不能排除完全包含、共面接触或未检查对象。输入场景 SHA-256 与运行自查记录相符，见[检查脚本](audit_selected_surfaces.py)。

### 3. 最终自查回答了比“没有穿模”更窄的问题

C 第 117 次调用及最终 `qa_report.json` 记录的是：

- 是否超出房间外包络；
- 床—床头柜、搁板—显示器、右窗帘—桌面等五项指定方向间距；
- 若干封闭单体的非流形边数、对象数量，以及保存与重新打开结果。

这些检查有价值，但房间内的两个物体仍可能彼此相交，封闭且流形的两个物体也仍可能互穿。右窗帘距桌面 **0.012 m** 并不能回答它是否穿过窗框。该最终检查以 `MESH` 对象为主，窗框、外饰线和横档实际为 `CURVE`；即便只扩展网格列表，也会漏掉这些关键邻居。

因此，本次问题可以具体表述为：**验收覆盖的对象关系与用户在意的对象关系不一致。** 频繁 `see`、读取 beauty render 或成功重新打开文件，没有补足这些遗漏。[脱敏工作流证据](results/arm-c-workflow-evidence.json)记录了对应调用索引、检查项目和自查声明。

### 4. 完整审计失败后，替代检查没有补齐覆盖范围

C 第 104 次 `blender_rt_plan(op="audit_scene")` 返回 `ok:false`，原因是无头 worker 的预加载发生 `NameError: __file__ is not defined`。事件外层仍被记为 `tool_result.status="completed"`，说明工具返回已完成，不能据此认为场景审计通过。

DSH 随后写了自查、修复了一部分拓扑问题，并明确标注缺少独立 reviewer；这种如实降级应保留。但替代检查没有覆盖窗帘—窗框、兔子—枕头或枕头互相之间。读取日志和最终成图后仍未补齐这些关系，因而留下了可见与可测的相交。

这也说明我们的现有 skill 仍需改进：它已经要求检查相交、重新打开和独立 QA，但本次运行没有把这些原则稳定地转化为必做的邻接检查。桥提供执行和观察能力，skill 需要把检查时机、对象范围和失败后的动作写得更具体。

## 我们的解决方案

### 本 PR：固定证据和组合边界

1. 记录预检和正式运行实际加载的 skill，不再以空壳文件存在代替隔离成功。提供 `prepare_bridge_only.py`，校验原版入口哈希，只修改隔离副本中的 skill 注册；桥和插件其他工具保留。
2. 保存 A、B、C 的成图、真实运行状态和脱敏调用序列；B 的中断与续接分开记录。保存 C 的检查范围、审计错误及最终场景的定向几何证据，不把自查的局部通过写成全场景无穿模。
3. 通过固定版本的 npm 包使用第三方插件，仓库不分发其源码或 bundled skill；保留版本、来源和许可范围说明。这里使用的仍是第三方桥。

本 PR 的价值是证明实时桥与我们的 skill 组合可用、插件自带建模 skill 在本案例中可替换，并把下一步要修的工作流问题变成可复核的具体案例。

### 下一 PR：只修改我们的 skill，然后从头复跑

以 C 为优化前基线，桥配置、插件修改方式、模型可记录参数及**完整提示词**保持一致，只修改我们的 skill 工作流；不修改插件、桥或本次场景，不追加人工修复提示。下一次仍从空场景开始，避免把现有场景修补当作 agent 工作流改善。

建议将 skill 中已有的原则细化成以下执行要求：

1. **建模前列出相邻关系。** 对窗帘—窗框/横档/墙、兔子—枕头/床面、枕头—枕头逐项声明允许接触、预期净空和禁止穿越；例外必须指明对象和理由，不能整体豁免软装。
2. **新增、移动、缩放或重建后重查邻居。** 相机可见性调整不能跳过空间关系检查；将发生变化的对象及其邻居标为待复查，结果绑定到当前保存场景。
3. **用分层检查覆盖实际对象类型。** 包围盒用于筛选候选；疑似相交再检查世界坐标中的求值几何与局部图，包含有厚度的曲线和修改器。单体拓扑、场景外包络和对象间关系分别报告。
4. **审计失败必须留下未完成项。** 读取内部 `ok`、错误和实际报告内容；替代检查必须说明覆盖了哪些失败项目。没有等价检查证据的项目标为未验证，不能据 `completed`、截图数量或文件存在判定通过。
5. **对保存结果审阅并闭环。** 对两侧窗帘、兔子和四个枕头进行定向近景与几何复查；修复后重查同一关系及受影响邻居，记录允许的接触与仍未解决的问题。沿用有限返修预算，对新候选复查变化及受影响区域，避免无新证据时反复扩展审计或重新渲染；独立 reviewer 不可用时继续明确写自查。

下一 PR 的验收应比较优化前后是否主动列出这些关系、变换后是否重查、失败时是否正确降级，以及最终相交是否减少。检查依据对象的语义关系匹配新场景；本 PR 的脚本只针对 C 的现有对象名，不能直接拿对象缺失当作新场景通过。调用次数与耗时作为附带数据，不代替几何与画面结果。

这些是待验证的改进方案，本 PR 尚未证明它们已经消除了穿模。
